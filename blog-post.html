Building a Zero-Trust Temporary Admin Access Workflow on macOS

How we replaced the "just make them a local admin" workaround with a Slack-approved, time-limited, fully audited elevation pipeline.

AWS Lambda Iru MDM SAP Privileges Slack DynamoDB EventBridge Node.js macOS

The Problem

Every IT team knows the conversation. A developer needs to install a dependency. An engineer needs to run a system-level diagnostic. A designer needs to update a font cache. The ask is always the same: "Can you just make me a local admin for a bit?"

The traditional answers are both bad. Option A: give them permanent local admin rights, accept the expanded attack surface, and hope they don't accidentally break their system or run a malicious installer. Option B: have IT remote in every single time, creating a bottleneck that interrupts both the user and the IT team.

We wanted a third path: just-in-time admin access, approved in Slack, time-limited to 30 minutes, and fully audited. No persistent privilege. No IT babysitting. A complete audit trail of every command run during the window.

Goal: Users get self-service access in under 60 seconds. IT maintains approval control. Every session auto-expires. Every sudo command is logged and shipped to the Slack thread.

How It Works

1
User opens Iru Self Service and clicks "Request Admin Access" A script prompts for a reason via osascript dialog, collects device identity (hostname, serial), and POSTs a signed request to an API Gateway endpoint.
2
IT receives an interactive Slack approval message The request includes user, hostname, serial, and reason. Approve/Deny buttons are shown with a confirmation dialog. The message is posted to a dedicated IT channel.
3
IT clicks Approve — Iru tag assigned + background approval monitor detects approval The elevation tag is added to the device. A background LaunchDaemon (installed by the Self Service script before it exits) polls the /status endpoint every 20 seconds. When it detects approval, it calls iru run directly on the device — the fastest path to processing Library Items without a full inventory collection. The user sees an "approved" alert within 20 seconds and is elevated shortly after.
4
Device runs elevation-start.sh via Iru Library Item The script calls PrivilegesCLI --add to grant admin, enables a sudoers drop-in for command logging, notifies the backend to start the 30-minute timer, and installs a network monitor LaunchDaemon.
5
EventBridge sends a 5-minute warning DM, then fires expiration at T+30 Timers are anchored to when the device confirms elevation — not when IT clicks Approve — so the full 30 minutes is always available. EventBridge schedules auto-delete after firing.
6
On expiration, Iru removes the tag and collects the sudo log A second Iru tag triggers collect-sudo-log.sh, which reads the sudoers logfile, ships it to the backend, and the backend uploads it as a file attachment in the original Slack approval thread.

Architecture

The backend is a fully serverless AWS SAM application. There's no always-on infrastructure — all compute is Lambda functions invoked by API Gateway or EventBridge Scheduler.

API Gateway + Lambda

9 Lambda functions handle request intake, Slack actions, device confirmations, log receipt, status polling, and expiration. All endpoints are behind API key authentication.

DynamoDB

Single-table design stores each request's full lifecycle: status, timestamps, Slack thread IDs, Iru device ID, and actor identity for every state transition.

EventBridge Scheduler

One-time schedules are created per session for the 5-minute warning (T+25) and expiration (T+30). Schedules auto-delete after firing via ActionAfterCompletion: DELETE.

Iru MDM

Two Iru tags act as a signal layer. Assigning the elevation tag triggers the Privileges profile. Assigning the log-collection tag triggers log shipping. Device-side iru run forces immediate Library Item processing — blankPush only triggers an MDM check-in and cannot run custom scripts.

SAP Privileges

Open-source macOS app from SAP that provides controlled, time-limited local admin elevation via a LaunchAgent. Scoped via a Iru configuration profile so it only activates on tagged devices.

System Keychain

The shared API key is stored in the system keychain (accessible by root) via a provisioning script run once at device setup. Scripts retrieve it at runtime — never hardcoded.

The Slack ↔ Lambda Handshake

Slack requires a 200 response within 3 seconds of an interactive action. But processing an approval — hitting Iru, writing to DynamoDB, creating EventBridge schedules — takes longer. The solution is a two-Lambda pattern:

  1. handleSlackAction verifies the Slack HMAC-SHA256 signature, extracts the action, and immediately invokes processSlackAction asynchronously (InvocationType: 'Event').
  2. handleSlackAction returns 200 to Slack within milliseconds.
  3. processSlackAction runs independently and handles all the heavy work.

Actor identity (Slack user ID and username of the IT admin who clicked) is forwarded from handleSlackAction to processSlackAction in the async payload and stored in DynamoDB for the audit trail.

Timer Anchoring

An early design mistake: the 30-minute timer was started at approval time. But there's latency between IT clicking Approve and the device actually being elevated — MDM check-in, Iru running the script, PrivilegesCLI executing. A user could lose 3–5 minutes of their window before they even had admin.

The fix: elevation-start.sh POSTs to a /start endpoint when elevation is confirmed on the device. The backend creates the EventBridge schedules from that timestamp. The user always gets a full 30 minutes from the moment they're actually elevated.

# elevation-start.sh — notify backend that elevation is confirmed
HTTP_STATUS=$(curl -s -o "$ELEVATION_RESPONSE_FILE" -w "%{http_code}" \
  -X POST "$API_ENDPOINT" \
  -H "Content-Type: application/json" \
  -H "x-api-key: $API_KEY" \
  --max-time 15 \
  -d "{\"requestId\":\"$REQUEST_ID\",\"serial\":\"$SERIAL\"}")

Security Features

After ten rounds of security audits, the system incorporates defense-in-depth across every layer:

Slack Signature Verification

Every Slack webhook is verified with HMAC-SHA256 using the signing secret. Requests older than 5 minutes are rejected to prevent replay attacks. Timing-safe comparison via crypto.timingSafeEqual.

DynamoDB Conditional Writes

All status transitions use ConditionExpression to enforce valid state machine transitions atomically. A race between two IT admins clicking Approve simultaneously results in exactly one approval, not two.

Input Validation Everywhere

UUID format validation on all device-facing endpoints. Field length limits (reason: 500 chars, hostname: 255, serial: 14). Email format validation. Serial number validated as 8–14 uppercase alphanumeric on the device before embedding in generated scripts. All Lambda endpoints reject non-object JSON bodies (arrays, bare strings, null).

Slack mrkdwn Injection Prevention

All user-controlled fields are passed through escapeSlack() before embedding in Slack Block Kit messages. Escapes &, <, > to prevent link injection via Slack's <URL|text> syntax.

Device Identity Binding

The serial number stored at request time is validated against every subsequent device call (/start, /log, /revoke-network-loss). A device can only interact with its own request — not another device's session.

Network Loss Revocation

A LaunchDaemon polls every 60 seconds. If network is lost, PrivilegesCLI immediately removes admin. When connectivity returns, the device notifies the backend. The status check captures HTTP response codes separately — the body is only parsed on a confirmed 200 response. Auth errors (401/403) trigger fail-secure revocation rather than retrying.

IT Slash Command

/admin-status lets designated IT admins query active sessions directly from Slack. Access is restricted to a configured allowlist of Slack user IDs — any other user receives an error. Empty allowlist defaults to denying all access (fail closed).

Off-Hours Delegation

Optional off-hours auto-approval routes requests to an on-call IT admin when business hours are outside the configured UTC window. Configuration errors (invalid hours, missing on-call ID) fail closed — requests are held for manual review, never auto-approved on misconfiguration.

Transient Failure Resilience

Iru API calls use exponential backoff (1s, 2s) for 5xx and 429 responses — up to 3 attempts. 4xx responses throw immediately without retry. This prevents a single Iru rate-limit event from dropping an entire approval or expiration operation.

Partial Failure Resilience

On expiration, elevation removal is the critical path — if it fails, EventBridge retries the whole handler. Log collection failure is non-critical: the record is still marked expired and IT is alerted via Slack, rather than leaving the session stuck in approved state.

Audit Trail & Delayed Notifications

Every state transition records the timestamp and actor. Approve/deny/revoke operations capture the IT admin's Slack user ID. User DMs on revocation or expiration are deliberately delayed until after sudo log collection succeeds — the user is not notified until the audit trail is secured.

Secrets Management

API key stored in the macOS system keychain — never in scripts or environment variables. Lambda secrets injected via AWS SSM Parameter Store at deploy time. Module-load-time validation ensures Lambdas fail fast if secrets are missing.

Metadata Isolation & Atomic Writes

Session metadata is stored at /var/root/.iru-elevation/meta.json (mode 600, directory mode 700) — root-only. Writes use a mktemp + mv pattern so a process crash mid-write never leaves a partial file. Plist-embedded time values are validated as numeric before writing.

iru run Mutex Lock

A file-based lock at /var/run/iru-run.lock prevents the approval monitor, network monitor, and expiration runner from calling iru run concurrently. Each caller waits up to 120 seconds before proceeding. The lock file lives in /var/run/ and is cleared automatically on reboot.

Post-Run State Verification

After each iru run --reset-daily, the approval monitor and network monitor verify that the expected system state change actually occurred (user is admin, or user is no longer admin). If not confirmed, a single retry fires after 120 seconds — accommodating Iru backend tag propagation latency — with a clear warning logged if the retry also fails.

Key Design Decisions

Why Iru Tags as Signals?

Iru Library Items can be scoped to specific device tags. By creating a Library Item (elevation-start.sh) scoped to the temp-admin-elevation tag, we get Iru's built-in delivery guarantees: retry on failure, run-at-install semantics, and immediate execution on blank push. We don't need to build our own device delivery mechanism — Iru handles it.

The same pattern applies to log collection: assigning the temp-admin-log-collection tag triggers collect-sudo-log.sh to run. When the script completes successfully, it removes the tag, preventing re-runs.

Why SAP Privileges Instead of dseditgroup?

Direct dseditgroup calls add the user to the local admin group and require a corresponding cleanup. SAP Privileges integrates with macOS's authorization model, provides a visible UI indicator to the user, supports an ExpirationInterval MDM key as a fallback safety net, and is open-source with active maintenance. The MDM profile approach also means the app is only functional on devices that have the profile — tagged devices only.

Why Two Iru Tags?

Separation of concerns. The elevation tag is removed on revocation or expiration. The log-collection tag is assigned on revocation or expiration. These two events are often simultaneous but not always (e.g., a network-loss revocation assigns the log tag immediately; the expiration timer also assigns it). Keeping them separate avoids race conditions and makes each Iru Library Item's trigger unambiguous.

Why EventBridge Scheduler Instead of SQS Delayed Messages?

EventBridge Scheduler supports named one-time schedules that can be deleted by name. This is critical for the revoke flow: if an IT admin manually revokes access at T+15, we need to cancel the T+25 warning and T+30 expiration schedules so they don't fire on an already-expired session. SQS delayed messages can't be cancelled after enqueuing.

Lessons Learned

The real attack surface is the device, not the backend

Most of the interesting security findings were in the shell scripts — unvalidated data embedded in generated scripts, metadata files with wrong permissions, python subprocesses without timeouts. The Lambda code is easy to reason about; the device-side bash is where subtle bugs hide. Treat shell scripts as first-class security artifacts.

Race conditions require database-level guards, not application-level checks

The pattern of "fetch → check status → update" is a TOCTOU race. Two concurrent Lambda invocations can both pass the check and both apply the update. DynamoDB's ConditionExpression moves the check into the atomic write operation. This is non-negotiable for state machines where each transition should happen exactly once.

Anchor timers to device confirmation, not approval

Any time you have an async pipeline (approve → MDM deliver → device run → confirm), the end user's experience is only as good as the last step. Anchoring timers to device confirmation rather than IT approval cost one extra API call but resulted in users always getting the full 30-minute window they were promised.

Iterative security auditing finds what point-in-time reviews miss

Running ten rounds of security audits on this codebase found meaningful issues in almost every round. Not because the earlier rounds were bad — but because fixing issues and adding features creates new surface area. Audit #6 alone found 11 findings introduced by the slash command, off-hours approval, and reason classification features. Build security review into your iteration cycle, not just your launch gate.

Zero open findings is achievable — but accept risk explicitly, not by omission

Audit #10 closed all 12 remaining open findings. The four accepted-risk items (timing side-channels, SIGTERM suppression, async Lambda pattern, system keychain access) were each evaluated deliberately: the attack requires specific access that already implies compromise, or the fix would require architectural changes that break the MDM delivery model. Accepted risk with documented rationale is categorically different from unfixed risk with no explanation.

New features are new attack surface — review them immediately

The slash command was the highest-severity new finding: Slack signature verification was in place, but no user authorization check existed. Any workspace member could enumerate all active admin sessions. The fix was three lines. The gap between "implemented" and "authorized" is where high-severity findings live.

Fail closed beats fail open, especially for access control

The off-hours auto-approval feature had a subtle misconfiguration path: invalid UTC hour configuration defaulted to treating all time as off-hours, auto-approving every request without IT review. The correct behavior is the opposite — if you're not sure it's off-hours, require manual approval. Any access-control feature that grants permissions by default on config error is a security risk.

Escape at the output boundary, not at ingestion

Early versions of the code tried to sanitize user input at ingestion time. This leads to double-encoding bugs and false confidence. The correct approach: store raw data, escape at every output boundary (Slack mrkdwn, JSON, shell variables). Each output context has different escaping requirements.

Never call a process runner from within a script being run by that process runner

elevation-start.sh was calling iru run at the end of its own execution — but this script runs inside a iru run triggered by the approval monitor. The Iru agent holds an internal lock during execution; a nested iru run waited indefinitely for that lock, freezing the outer agent. The fix was a single line removal: iru run inside a Iru script is a deadlock by construction.

Verify the check actually checks something

The UTF-8 validation in receiveLog was Buffer.from(x).equals(Buffer.from(x)) — a tautology that always returns true and never rejects anything. It passed code review because it looked correct. The Audit #8 find: always test security checks with an input that should fail. A check that never rejects is not a check.

Recently Shipped

  • Background approval monitor: The Self Service script now exits in under 5 seconds. A background LaunchDaemon installs at request time and polls for approval every 20 seconds — no more blocking the Iru Self Service app for minutes.
  • Removed all blankPush calls: blankPush triggers an MDM check-in, not a Library Item run — it cannot invoke custom scripts. All server-side blankPush calls were removed; device-side iru run is now the exclusive mechanism for picking up tag changes.
  • iru run mutex lock: Three background daemons (approval monitor, network monitor, expiration runner) could previously call iru run concurrently. A file lock at /var/run/iru-run.lock serializes all iru run invocations, eliminating agent contention.
  • Delayed revocation DMs: Users are not notified when their access is revoked or expires until after sudo logs are successfully collected. The audit trail is secured before the user learns the session ended.
  • Slack original message lifecycle: The original approval message (with Approve/Deny buttons) is now updated to a final "completed" state when log collection succeeds — showing the outcome and timeline, with all buttons removed.
  • Fixed nested iru run deadlock: elevation-start.sh was calling iru run at the end of its own execution — but it runs inside a iru run. The Iru agent holds an internal lock during execution, so the nested call deadlocked the outer agent. Removed the redundant inner call.
  • Switched to iru run --reset-daily: Plain iru run skips Library Items the agent has already processed today. --reset-daily forces full re-evaluation, ensuring the elevation or log-collection script always runs when the tag is assigned — even if the agent's daily run already completed.
  • Post-run state verification with 120s retry: The approval monitor now confirms the user is actually admin after iru run completes. The network monitor confirms admin has been removed after revocation. If the expected state isn't confirmed, a single retry fires after 120 seconds — absorbing Iru backend tag propagation latency without requiring the user or IT to intervene.
  • PID-aware mutex lock: The iru run lock file now stores the holding process's PID. If the holder was killed with SIGKILL, the dead PID is detected via kill -0 and the stale lock is removed immediately — previously the 120-second timeout was the only recovery path.
  • Atomic daemon cleanup: The approval monitor cleanup now removes the plist file before calling launchctl remove <label>, eliminating the window where a stale plist could exist on disk if the script was interrupted mid-cleanup.
  • Off-hours failure visibility: If off-hours auto-approval fails (Lambda quota, permissions error), a warning is now posted to the IT Slack thread immediately — IT sees the request needs manual review rather than it silently staying in pending indefinitely.
  • Degraded log warning: If timezone conversion fails during log collection, a visible [WARNING: unified log source skipped] header is prepended to the uploaded log file so IT knows the collection was degraded.
  • Iru 4xx error logging: The first 200 characters of Iru API 4xx error responses are now logged — enabling diagnosis of "device not found" vs "invalid tag" failures without a separate API call.
